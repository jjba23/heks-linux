# Vision

Heks GNU/Linux is a library of Guile Scheme modules that render the configuration files a GNU/Linux desktop actually parses: Niri's KDL, whelk's `settings.scm`, WezTerm's Lua, a KIWI description for a bootable image. It is not a distribution and does not want to be one — it is the provisioning layer that sits between a set of parameters and the programs those parameters configure. This document is about where that layer should be in a few years, and which of the seams it has already cut are worth widening first.

## Where heks-linux is today

The tree holds thirty modules under `src/heks-linux/`, three package backends (`packages/zypper.scm`, `packages/flatpak.scm`, `packages/nix.scm`), roughly fifteen thousand lines of Scheme, and twenty-six Veritas specs that render whole configuration files and assert on the text the real program will parse. The surfaces covered are the session (Niri, whelk, the wallpaper engine, the capture scripts), the terminal and editor bridges (WezTerm, an Emacs bridge, a Bash bridge), the browser (Zen `user.js`), the file-and-identity modules (Git, SSH), the container modules (Podman, Distrobox), the media stack (RMPC, Cava) and the image.

The palette registry carries about forty-five palettes, each a list of semantic keys (`text`, `primary`, `background`, and their siblings) rather than a list of colours, plus a contrast-ratio calculator that picks a legible ink against any background instead of trusting the palette author. One palette symbol drives GTK, dconf, whelk, WezTerm, Lambdock, btop, the Tela icon accent, WhiteSur cursors and the wallpaper set.

The second half of the project is not dotfiles at all. `image.scm` renders a KIWI description in Scheme — the XML that names the distribution and its repositories, the `config.sh` that runs inside the chroot, the `images.sh` that names the artefact, and a `root/` payload — so the same parameters that render a session also render a live Slowroll ISO and an installable disk image. `capture.scm` is a 1,200-line program that drives `grim`, `wl-screenrec`, `wf-recorder`, `satty` and `ffmpeg` behind one menu, with a `doctor` that names what is missing. `zen.scm` finds every Zen profile on the machine, including the one inside the Flatpak sandbox, and writes `user.js` into each. `toon.scm` is the small half of a GTK4 program that lives in another repository, and it mostly exists to retire the three HTML pages it replaced.

The size distribution is itself an account of where the work is: `whelk.scm` at about 580 lines and `niri.scm` at about 1,480 hold the session's shell and its policy, `capture.scm` and `palette.scm` at about 1,200 each hold a program and a registry, and `prelude.scm` at 490 holds the primitives everything else is built from — the serialisers, the atomic writer, the symlink chase, the override loader.

Four decisions are load-bearing and constrain everything that follows. They are worth stating plainly, because most of what this document asks for is a consequence of them rather than a departure from them.

1. Configuration is a function of settings, and settings are parameter objects rather than arguments. This is what makes a per-machine override file possible without threading keyword arguments through twenty call frames — and it is also why overrides are *code*, evaluated with `load` inside the module's own namespace, not data a parser could check.
2. Every module is independently useful. There is no central registry, no daemon and no global mutable state; `install-whelk-config` does not know that Niri exists. The price is that nothing in the tree knows the complete set of surfaces a palette reaches.
3. Prefer a data structure over a template string. whelk's settings are a Scheme program, Niri's config is a tree of records serialised to KDL, WezTerm's is an association list rendered to Lua. This is the reason the modules can be unit-tested at all.
4. A written file is atomic and symlink-preserving: the content goes to a temporary file beside the real target, permissions are applied before the rename, and an eight-hop symlink chase decides what the real target is. One of the readers of that promise is the palette picker re-rendering itself from inside itself.

What is honestly weaker: openSUSE Tumbleweed-Slowroll is the validated path and one person validates it daily; the Debian and Fedora material is a guide, not a tested route. The internationalisation seam exists — `G_`, `setup-i18n`, `heks-linux-language` — with a catalogue for the prose it covers. `packages/` has one protocol its three backends implement, and no Debian or Fedora backend at all.

Two smaller asymmetries matter more than their size. The capture stack is the only surface with a `doctor`, so it is the only surface that can tell you what it is missing. And a render is one-shot: `maak home-reconfigure` writes, reloads, and forgets. There is a `maak check-updates` that reports what has an update without changing anything, which is the right shape for a read-only task, but there is no equivalent for the files this project itself owns.

What the tree is genuinely good at, and should not lose while fixing the rest: every module's commentary explains *why* it exists and what it refuses to do (`toon.scm` explains that it does not render, serve or watch anything; `image.scm` explains that the store is rendered by the build rather than by a first boot); the docstrings are the API reference, because CI publishes them on every push; and the specs assert on the text a real program will parse, including the contrast of the bar's ink against its own material. That combination — rationale, reference and text-level proof — is rarer than any feature list, and it is the thing worth protecting when the changes above start to arrive.

## The vision

1. **Every number two surfaces share is one value with one test.** `whelk-window-radius` already exists as a single value because whelk rounds its launcher with it and Niri rounds the launcher's shadow with the same number; a shadow at a different radius pokes out behind the corners. That is the correct pattern, and it is currently the only instance of it. In a few years an invariant that spans two files should be a first-class thing in the tree, cheap to add and impossible to break silently.
2. **Palette coverage is total by construction.** A palette carries colours and an accent; the GTK theme and cursors are the one set the tasks install, the Emacs theme is the palette's own name with a named fallback, and btop and Lambdock take their brightness default unless a palette is close enough to a named look to earn an exception. The suite asks every registered palette for every surface, so a surface with no answer is a failing test rather than a component that kept the old colours. The wallpaper set is the one surface still named by hand.
3. **The image is offline-complete and reproducible to a hash.** The same modules that rendered the live session rendered the installed disk, the Guix store those modules need is inside the artefact, and a first boot that has no network still produces the desktop.
4. **A second distribution is a tested backend, not a document.** `packages/` has one protocol its three backends implement; a Debian or Fedora implementation passing the same specs the zypper one does is what would make the guides in `docs/` describe a path somebody's CI runs, instead of a path somebody's laptop ran once.
5. **What is on disk can be compared with what the tree would write.** A render today writes and moves on; nothing notices that a file was hand-edited three months ago, or that a module's output changed shape while the machine kept the old copy. A read-only audit — the same shape as `maak check-updates`, which reports and changes nothing — is what turns "reconfigure and hope" into a diff.

The thread running through all five is the same one: this project is unusually good at producing correct text and unusually bad at knowing whether the machine matches it. The atomic write solved *how* to write; it did not solve *what was written, by whom, and whether it still holds*. Most of the engineering below is on the second half.

The ordering matters less than the direction. The shared-value work and the palette coverage work are both weeks, not years, and both make everything after them easier: a tree that can prove its surfaces agree is a tree where the image can be trusted, and a palette that cannot be half-applied is a palette a contributor can add without owning eleven renderers.

None of the five asks for a new abstraction over the existing ones. Each is a consequence of a decision already taken: the shared value follows rule 3 (a data structure, not a template string), palette coverage follows rule 2 (modules do not know about each other, so something else must), the tested backend follows from the guides that already exist, and the audit follows from `install-config-file!` having been made atomic in the first place. That is deliberately the cheapest kind of vision: the architecture is not the thing being changed.

## Features that are in scope and not built yet

These are not wishes; each one is a seam the code has already cut and left open.

- **A boot test for the image.** `maak image-check` validates the description through KIWI's own reader and stops there. *The hard part* is a VM with a serial console in CI, and knowing which of a live boot's many possible failures is the one worth asserting on.
- **`doctor` for every surface.** The capture module has one: `heks-capture doctor` says which of the tools it drives are missing and which task installs them. *The hard part* is that a module's runtime dependencies are not the same set as its package list entry — some are optional, some are fallbacks, some are only reached from one keybinding.
- **A recorded state for the drift audit.** Nothing remembers what was written, so a file cannot be compared against the render that produced it. *The hard part* is that a user editing a generated file on purpose is legitimate and must not be reported as damage; the difference between drift and intent needs a record, not a heuristic.
- **A session-level rollback.** A palette switch re-renders a dozen files and reloads the surfaces; if the eighth render raises, the first seven are already on disk and the desktop is half-repainted. `install-config-file!` makes each *file* atomic, and nothing makes the *set* atomic. *The hard part* is that the reload is performed by other processes — Niri, whelk, Lambdock — and undoing a switch means knowing which of them accepted what.
- **The keyboard reference as data.** The bindings are written once into `niri.scm` as data, described again in `docs/keybindings.org`, and drawn again in the reference window the bar's `?` button opens. Nothing in this tree asserts that the three agree, and the reference is the one a user trusts in the moment they need it. *The hard part* is that the config is a data structure while the reference is prose about intent, so joining them needs something better than transcription.
- **Pins with an integrity story.** `icons.scm` pins Tela to a tag, `eca.scm` pins the client to a version and asks the installed copy what version it is, `zen.scm` side-loads a signed uBlock Origin build. No module verifies a downloaded artefact against a checksum recorded in the tree. *The hard part* is a supply-chain answer that is honest about what it can promise: a tag can be moved, a release asset can be replaced, and a Scheme-side checksum is only as trustworthy as the commit that holds it.

## New features that would be worth having

- **`heks-audit`.** Render every module into a scratch directory and diff it against the live tree: what would change, what already differs, what a module no longer writes at all. Read-only, non-zero exit for CI, no prompt. In the character of a project whose writes are already atomic and whose `check-updates` already reports without touching.
- **Profiles as data.** A named bundle of every parameter — palette, faces, modules, image recipe — so a laptop and a desktop differ by one file, and that file can be diffed, branched and published. Bounded by the existing contract: overrides are code evaluated in a module's namespace, so a profile that is *only* parameters has to be distinguished from an override that is *code*.
- **A generated surface manifest.** One table, built from the modules themselves: each surface, the files it writes, the programs that read them, the package that provides each program, and the keybinding that reaches it. The keyboard reference, the `docs/` tables and the doctor output should all be views of it rather than three hand-maintained lists.
- **Validation before writing.** Niri validates its own config (`niri validate`), and a bad KDL file is a session that does not come back. A pre-flight check that runs the target program's own validator where one exists, and reports rather than writes when it fails, is cheap insurance on a desktop whose failure mode is a black screen.
- **Wallpapers derived from a palette.** The wallpaper engine already keeps a catalogue and a palette-aware chooser and rotates on a systemd timer; generating the pair from the palette's own four colours would close the last surface still curated by hand. *(Speculative — this needs an image pipeline the tree does not have, and the taste question of whether generated wallpaper is good is not settled.)*
- **A second desktop session.** The modules assume Niri. A Sway or River session reusing the palette, whelk and Lambdock modules — but not the Niri binding table — would test whether "every module is independently useful" survives contact with a different compositor. *(Speculative, and a large amount of work for the evidence it produces.)*
- **A machine-readable description of the desktop.** Every fact this project knows about your session — palette, faces, monitor layout, the shell, the editor, the clone directory — already exists as a parameter. Exporting the resolved set as one document would let another program (a bug report, a screenshot caption, the About window, `heks-toon`) read them instead of re-deriving them, and would make a bug report reproducible by construction. *(Speculative in form; the parameters themselves are real, and the risk is that the export becomes a second source of truth.)*
- **A first-class "why".** Every design decision in this tree is explained — in module commentaries, in `docs/philosophy.org`, in the four ideas — but the explanations are prose a reader has to find. A convention that attaches a short rationale to a parameter or a rule, and can be printed beside it, would make the reasoning survive the person who wrote it. *(Speculative, and possibly worse than the existing commentaries; worth trying because the commentary convention is already this project's strongest habit.)*

The pattern in the speculative items is worth naming: each is an attempt to move a fact from prose into data, so that a test, a page and a renderer can all read it. That is the same move `whelk-window-radius` already made, and it is the only kind of change this tree has repeatedly been able to absorb.

## Contributions that would move the needle

1. **A complete palette.** Add one end to end: the semantic keys, the ink that stays legible on it, the Tela accent, the wallpaper set, and - only where the defaults are wrong - an exception in the Emacs, btop or Lambdock table. Why it is a good task: the specs already assert contrast, so the suite tells you when you are wrong; you learn the whole registry in an afternoon; and every gap you hit is a gap this document is about.
2. **One cross-surface invariant, expressed as a spec.** The whelk/Niri radius pair is the pattern; the second instance is the one that matters, because it forces the question of where a shared value lives when rule 2 says there is no central registry. Why it is a good task: it is a few dozen lines, it cannot be done by guessing, and it pays out on every future change to either surface.
3. **A distribution guide you actually run.** Not a translation of the Slowroll path — the list of packages you genuinely installed, the things that were missing, and the module that needed a change to work there. Why it is a good task: it is the cheapest way to find the real portability seams, and it is the only way `docs/debian-guide.org` and `docs/fedora-guide.org` stop being documentation of an intention.
4. **A `doctor` for one surface.** Pick the surface whose failure is least self-explanatory — the capture stack and the music stack are the two candidates — and make the task end by saying what is missing and which task installs it. Why it is a good task: small, self-contained, immediately useful to the person filing the bug report.
5. **A docstring the API reference gets wrong.** The published reference is generated from docstrings by `maak deploy` on every push to `trunk`, so a docstring is not decoration — it is the manual. Why it is a good task: an hour, no risk, and it is the contribution that makes the next reader's afternoon shorter.
6. **A spec that renders a module and diffs it against the last one.** The suite asserts *properties* of rendered output today; a blessed-output comparison would catch the changes nobody described. Why it is ranked low: it is easy to do badly, and a golden file that is regenerated whenever it fails is worse than no golden file at all.

The ranking is value per hour, not importance. Items 1 to 4 are all a few days of work and each one removes a recurring cost: the palette surface that would otherwise have to be guessed, the invariant you have to remember, the guide nobody tested, the bug report that starts with "is `grim` installed?". The distribution backend is the one that changes what the project *is*, and it is the one that cannot be hurried.

There is a fifth kind of contribution not on this list because it has no artefact: telling the project which distribution you run and which module broke there. The Debian and Fedora guides exist because someone did that once, and the reason statement 4 is a statement rather than a wish is that the information is not currently being collected anywhere.

## Compared to related projects

| Project | What it is | Where heks-linux differs |
|---|---|---|
| GNU Guix Home | A declarative home environment described in Scheme, built through the Guix store | Heks writes files for software Guix does not configure (Niri, whelk); it manages no store, installs into `$HOME` conventionally, and runs on distributions that have no Guix. |
| Nix Home Manager | The same idea in Nix, with a typed option schema and a module system | Home Manager has real option types and merging, which heks has nothing like; heks trades that for rendering third-party formats exactly — KDL, rasi, Lua — rather than generating them from a Nix data structure. |
| chezmoi | A dotfile manager with templates, secrets and a git-backed source state | chezmoi templates text; heks evaluates a program that returns a data structure. chezmoi knows what it wrote last time; heks does not, and that is the gap this document's audit item is about. |
| GNU Stow | A symlink farm from a package directory into `$HOME` | Stow links whole files and stops there. Heks writes atomically, writes *through* a symlink so a dotfile linked into a repository stays linked, and sets permissions before the rename. |
| Omarchy | An opinionated Arch-plus-Hyprland setup, delivered as a curated install | The closest thing in spirit: a desktop someone assembled and handed over. Omarchy is a snapshot of one machine's taste; heks is a program whose output can be re-derived, re-tested and re-targeted. |
| Universal Blue / bootc images | Atomic, image-based GNU/Linux desktops built in CI and updated as images | They own the whole operating system and are excellent at it. Heks deliberately does not: the image is a *consequence* of the modules, and the same modules work on a machine that never boots it. |
| Sway/Hyprland dotfile collections | Large hand-written configuration repositories | Those are the artefacts heks replaces. The difference is testability: a dotfile collection can only be checked by logging in, and a Heks module is asserted on the text it renders. |
| Kickstart, AutoYaST, cloud-init | The image-time provisioning formats each distribution already ships | They describe a machine once, at install time, and know nothing about the desktop that runs afterwards. Heks generates KIWI's `config.sh` and `images.sh` from the same Scheme parameters the session reads, so the image and the session cannot disagree about a palette or a hostname. |
| Ansible, Salt, Chef | Agentless or agent-based configuration management with imperative modules | They are built for fleets and idempotence against a remote inventory. Heks is built for one machine whose configuration is a data structure; it has no inventory, no transport and no convergence loop, only a render. |

What the others do that heks could still add: Home Manager's typed options and conflict resolution are a genuinely better answer than parameter objects for *checking* a configuration, and chezmoi's record of what it last wrote is the mechanism the drift audit needs. Both are adoptable without giving up anything in rules 1 to 4. Omarchy and the large Hyprland collections are the honest competition for attention rather than for technology: they win on the first hour, and they lose the moment a second machine, a second palette or a second person is involved.

Where heks is ahead and should stay ahead: it renders formats no declarative system models, it is honest about the difference between a guide and a tested path, and its specs assert on what the real program will parse rather than on what its own abstraction believes. A declarative system that only knows its own schema cannot test that. The temptation to become a distribution — to own the base system, the kernel, the bootloader — should be resisted for the same reason: it would replace the part of this project that is defensible with the part that is a commodity.

## In the long run

The multi-year bet is that a desktop's settings are a program with invariants, and that the invariants — not the settings — are what separate a maintained system from a hobby. Everything above is an instance: the shared radius, the total palette, the tested backend, the audited tree.

The second bet is that the distribution should become replaceable. Heks names openSUSE as the official path and means it, but the layer it actually owns is distribution-agnostic by construction; the day a second backend passes the same specs, the distribution becomes an implementation detail of the packages module. That is a far more durable position than being a good openSUSE setup.

The third, quieter bet is on Guile as the configuration language rather than merely a nicer YAML. A REPL into a running session, a module that is independently callable, a data structure instead of a template string — those are the reasons this project can be tested at all, and they are the reasons to keep refusing the shortcut that would make one surface easier and the whole thing unprovable.

The fourth bet is about who this is for. Today Heks is a personal system that grew a community: one author, one validated path, one daily driver. If the five statements above hold, the honest position changes — not to a distribution with users to support, but to a *library* with consumers, where somebody's Fedora laptop and somebody's image build are both first-class and neither requires the author to have that machine. Getting there means the specs, not the author's session, become the definition of working; that is a cultural change as much as a technical one, and it is the one most likely to be resisted.

What would make all four bets wrong is worth saying too. If the compositor ecosystem consolidates around a declarative configuration format of its own, the rendering half of this project loses its reason to exist and the argument moves to the image and the palette. If Guile's ecosystem stalls, the language bet fails regardless of how good the design is. And if one person's daily driver remains the only validated path forever, then Heks is a very well-documented personal setup — which is a perfectly good thing to be, and not the same thing as what is described above.

## How to read this document

This is a direction, not a roadmap with dates. The items under "in scope and not built yet" are the ones the code has already committed to by cutting a seam; the items under "new features" are proposals, and the three marked speculative are marked because they are. Anything here can be argued with in an issue, and the argument is more useful than the document.

A reader who knows this project should be able to use the five statements as a test of any future pull request: does this make a shared value provable, a palette complete, a path tested, or a difference visible? If it does none of those, it is probably still welcome — this is a personal system that grew a community, and taste is a legitimate reason to change it — but it is not what this document is arguing for.

*This document describes intent, not commitments; nothing in it is promised, and the code and its tests remain the only account of what Heks GNU/Linux does.*
