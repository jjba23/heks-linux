#+title: Installing Heks on Debian, step by step
#+options: toc:nil

[[file:../README.org][← Back to the README]]

Debian is the second target.  Everything above the machine is the same as on
Void - the same modules, the same renderer, the same files - and what differs is
the two things this tree asks the distribution for: a package manager and an
init system.  Debian has apt where Void has xbps, systemd where Void has runit,
and both are supported answers rather than ports: the package list lives in
~src/heks-linux/packages/apt.scm~, and the init system is read from the machine
itself, so there is no override to write before the first task runs.

[[file:install-void.org][The Void page]] is the same install in Void's words, and
[[file:installation.org][Installation]] is the map with the requirements every
target shares.

#+begin_quote
*What this page assumes:* Debian 13 (~trixie~) or newer, glibc, ~amd64~ or
~arm64~, a network, and an account in the ~sudo~ group.  Debian is where Heks
runs second: it is exercised less than Void, its package list is the smaller of
the two, and the things Debian does not carry are named below with what to do
about them rather than left to be discovered.
#+end_quote

** 1. Install what Guix's installer needs

The official Guix installer downloads with =curl= and verifies what it
downloaded with =gpg=.  ~git~ is what the pinned channels arrive with.

#+begin_src shell
sudo apt-get update
sudo apt-get install --no-install-recommends curl gnupg git uidmap
#+end_src

=uidmap= is not decoration.  Guix builds as an unprivileged user through
=newuidmap= and =newgidmap=, and Debian puts those two in a package of their
own: without it the installer stops at the first step with
~Missing commands: newgidmap~, having installed nothing.  Void's =shadow=
package ships them, which is why the Void page does not name a package for this.

** 2. Install GNU Guix

Guix is GNU's reproducible package manager, and the half of this tree that does
not depend on the distribution: the environments the modules render in are Guix
environments, pinned by ~channels.scm~.

The script below is Guix's own installer, fetched from Codeberg's mirror of Guix
- the copy that answers.  Savannah's cgit is the canonical one and the fallback,
and it served nothing at all for minutes at a time when this page was written,
which reads as a broken network rather than as a slow host.  ~bash -n~ is there
because half a download is a file that runs half of an installer.

#+begin_src shell
cd /tmp
curl -fsSL --connect-timeout 10 \
  https://codeberg.org/guix/guix/raw/branch/master/etc/guix-install.sh \
  -o guix-install.sh
bash -n guix-install.sh
chmod +x guix-install.sh
sudo ./guix-install.sh
#+end_src

If Codeberg is the one that is down, the same file is at
~https://git.savannah.gnu.org/cgit/guix.git/plain/etc/guix-install.sh~; the
=heks-setup= script tries those two in that order and refuses a download that is
not a whole script.

Answer *yes* to the pre-built binaries and to the local substitute discovery.  On
a machine with systemd - which is every Debian - the installer writes and enables
=guix-daemon.service= itself, which is the one thing the Void page has to do by
hand:

#+begin_src shell
systemctl status guix-daemon --no-pager
#+end_src

=active (running)= is the answer you want.  If it says the unit does not exist,
Guix's own documentation has the current unit file; the service is the same
daemon either way.

Add the Guix profile to your shell, if the installer did not:

#+begin_src shell
GUIX_PROFILE="$HOME/.guix-profile"
. "$GUIX_PROFILE/etc/profile"
export GUIX_LOCPATH="$HOME/.guix-profile/lib/locale"
#+end_src

** 3. Clone Heks and pin the channels
:PROPERTIES:
:CUSTOM_ID: debian-pinned-channels
:END:

#+begin_src shell
git clone https://codeberg.org/jjba23/heks-linux.git
cd heks-linux

install -D -m 644 channels.scm ~/.config/guix/trusted-channels.scm
guix pull --channels=channels.scm
hash guix
sudo systemctl restart guix-daemon
#+end_src

~channels.scm~ is a lock file: it pins the Guix revision and the
[[https://github.com/jjba23/guix-jointhefreeworld][jointhefreeworld]] channel
this tree was tested against, which is where =maak=, =veritas=, =scriba= and the
rest of the collection come from.  Treat it as one - ~maak update-guix~ is how
it moves.

The trusted-channels line is the one step people skip and the one that produces a
warning with no consequence: Guix only pulls a channel that carries an
introduction if the channel is trusted, and the file above is what says so.

** 4. Install Maak and Guile

#+begin_src shell
guix install glibc-locales maak guile
#+end_src

~maak~ runs every task in the tree.  Its config tasks wrap themselves in the
project's pinned manifest, so ~maak compile~ and ~maak test~ work from the
repository root without entering a shell by hand.

** 5. Install the desktop packages

#+begin_src shell
maak install-apt
#+end_src

That is the Debian list: the session and what it needs to draw (the floating
compositor, the Wayland portals, PipeWire and its PulseAudio-compatible server,
NetworkManager, the Mesa drivers Debian spells ~libgl1-mesa-dri~), the greetd
login prompt, the capture stack, Emacs, a small command line, and the toolchain
this tree's own tasks use - with ~--no-install-recommends~, so a Debian machine
gets the programs this tree names and not the ones apt thinks they would like.
It carries the same two things the Void list does that a curated list has to say
out loud: ~xdg-utils~ for the launcher's ~xdg-open~ and ~xdg-user-dirs~ for the
directories the session names, plus ~zip~ and ~unzip~ beside ~7zip~, and the Noto
emoji and CJK faces.  It lives in ~src/heks-linux/packages/apt.scm~ and is meant
to be read and edited; [[file:../test/veritas/unit/packages-parity-spec.scm][a
spec]] holds it and the Void list to the same desktop, requirement by
requirement.

=elogind= is not on it and does not need to be: Debian has systemd's own logind,
which is what =loginctl= asks for the power menu.

The login prompt is a service, and Debian's ~greetd~ package ships its own
configuration for it.  This tree's two files are the ones that say what the
prompt looks like and which sessions it offers:

#+begin_src shell
sudo install -d -m 755 /etc/greetd /etc/tuigreet
guile -L src -c '(display ((@ (heks-linux greeter) greetd-config)))' \
  | sudo tee /etc/greetd/config.toml >/dev/null
guile -L src -c '(display ((@ (heks-linux greeter) greeter-config)))' \
  | sudo tee /etc/tuigreet/config.toml >/dev/null
sudo systemctl enable greetd
sudo systemctl set-default graphical.target
#+end_src

A Debian that already runs a display manager has two programs wanting the
console: disable the other one, because two prompts on one screen are no prompt.

#+begin_src shell
sudo systemctl disable gdm3    # or lightdm, sddm, whichever this machine runs
#+end_src

The sessions the prompt lists come from =/usr/share/wayland-sessions=, and
Debian 13 has no Niri package to put an entry there: the compositor is built in
[[#debian-niri][the Niri section below]], and the entry that starts it is written by hand.
=niri --session= imports the login environment and starts Niri's own D-Bus
services, which is what =niri-session= does on a machine with systemd and what
works on one without:

#+begin_src shell
sudo install -d -m 755 /usr/share/wayland-sessions
sudo tee /usr/share/wayland-sessions/heks-niri.desktop >/dev/null <<'EOF'
[Desktop Entry]
Type=Application
Name=Heks Niri
Comment=The scrollable tiling session
Exec=niri --session
TryExec=niri
DesktopNames=niri
EOF
#+end_src

=TryExec= is what greys the entry out when the binary is not on the prompt's
PATH, which is the reason the Niri section below installs the built compositor
into =/usr/local/bin= rather than leaving it in =~/.cargo/bin=.

Nothing in the package list is Niri itself: a machine that logs in before
[[#debian-niri][building it]] gets the floating session and a greyed-out entry for the tiling
one.

** 6. Build and install the shell, the dock and the keyboard reference

whelk, Lambdock and heks-toon are not Debian packages, so this repository carries
their Debian packaging and builds them on the machine that will run them:

#+begin_src shell
sudo apt-get install --no-install-recommends build-essential \
    debhelper devscripts meson ninja-build pkg-config
maak deb-build              # one .deb per program, into dist/deb
sudo apt-get install -y dist/deb/*.deb
#+end_src

~maak deb-build~ fetches the release each program's recipe names - the same
version and the same SHA-256 the Void package uses, read from its template in
~packaging/void/~ - unpacks it, drops the Debian packaging from
~packaging/debian/~ in, and runs ~dpkg-buildpackage~.  The build dependencies
each package declares are the ones apt installs while it builds; Rust is a
toolchain download the first time, which is what makes this step the long one.

They are then packages: ~maak update-apt~ upgrades them with the rest of the
machine, ~apt remove~ removes them, and a session does not depend on a store
being up.  ~maak install-collection~ does the install half on either target,
whichever manager it finds.

Nix is not part of this step, and does not need to be installed at all unless
you want the development tooling: ~maak install-nix-packages~ is the language
servers and the debuggers, [[file:guides.org][the guides]] say what is there.

** 7. Render your home

#+begin_src shell
maak home-reconfigure
#+end_src

Then log out and back in: the prompt takes your account and password and starts
heks-niri.  Every surface the render wrote watches its own file, so the session
you land in is the one those files describe.

** What Debian does not carry

The Debian list is shorter than Void's on purpose, and these are the gaps worth
knowing before you go looking for them:

| *What*                | *Why*                                                                 | *What to do*                                                        |
|-----------------------+-----------------------------------------------------------------------+---------------------------------------------------------------------|
| ~niri~                | No Niri in Debian 13 at all, and the crate on crates.io is a placeholder that prints *niri cannot be properly installed with cargo*. | Build it from its own repository - [[#debian-niri][Niri itself]], below. |
| ~xwayland-satellite~  | No Debian package in any suite.                                       | Build it beside Niri - [[#debian-x11][X11, for the launcher]], below. |
| ~fd~                  | The package is ~fd-find~, and it installs ~fdfind~: Debian already had a program called ~fd~. | ~ln -s "$(command -v fdfind)" ~/.local/bin/fd~                       |
| ~rmpc~                | Not a Debian package.                                                  | ~cargo install rmpc~ (the Rust toolchain is in the list), or use another MPD client. |
| ~satty~               | Not a Debian package.                                                  | Nothing: the list carries ~swappy~, and ~heks-capture annotate~ drives either one. |
| ~wbg~                 | Not a Debian package.                                                  | Nothing: the wallpaper engine falls back to ~swaybg~, which the list installs. |
| ~socklog-void~        | It is Void's syslog, for runit; Debian's log is the journal.            | ~journalctl -b~; nothing to install.                                  |
| Font Awesome 6        | Debian 13 carries Font Awesome 4.7 as ~fonts-font-awesome~; the bar asks for the 6 Free face first. | Install the 6 Free face from its release - [[#debian-fonts][The icon fonts]], below. The bar falls back to 4.7 by itself. |
| Symbols Nerd Font     | ~fonts-nerd-symbols~ is in forky and sid, not in trixie.                | Install the symbols face from the Nerd Fonts release - [[#debian-fonts][The icon fonts]], below. |
| JuliaMono, Work Sans  | No Debian package.                                                     | Install the faces from their own releases; the fontconfig fallbacks cover the gap until you do. |
| Emoji and CJK         | Both lists carry them (~fonts-noto-color-emoji~, ~fonts-noto-cjk~), because a page of Japanese drawn as boxes is a fallback list that stops at Latin. | Nothing. |
| Source Serif 4        | Debian 13 packages no Source Serif 4: neither main nor contrib names one. | Install the face from Adobe's release, or let the fontconfig fallbacks answer; nothing else in the desktop needs it. |
| ~heks-snapshot~       | It is a BTRFS tool this tree's medium installs, and Debian's installer does its own thing with disks. | Nothing: snapshots are not part of the Debian path.                   |

Four of those rows are literal: ~maak install-apt~ used to name ~niri~,
~xwayland-satellite~, ~satty~ and ~fonts-nerd-symbols~, and on Debian 13 the
whole command stopped at the first name apt could not resolve, installing
nothing.  A name Debian does not carry is a name for this page, not for the
list, and [[file:../test/veritas/unit/packages-parity-spec.scm][the parity spec]]
now holds the four names out of it.

** What Debian needs that a Heks machine already has

Six things, and each one is a session that half-works without it.  All of them
are about being a guest on a distribution that was installed for GNOME.

*** Niri itself
:PROPERTIES:
:CUSTOM_ID: debian-niri
:END:

Debian 13 packages no Niri, in any suite.  Build it from its own repository,
which is what its README says - the crate on crates.io is a placeholder that
prints *niri cannot be properly installed with cargo* and exits:

#+begin_src shell
sudo apt-get install --no-install-recommends build-essential pkg-config git rustup
rustup default stable
. "$HOME/.cargo/env"
cargo install --locked --git https://github.com/YaLTeR/niri niri
sudo install -Dm755 "$(command -v niri)" /usr/local/bin/niri
#+end_src

Niri 26.04 needs ~rustc~ 1.88 or newer, and Debian 13 ships 1.85: a user-level
~rustup~ is the way round it, and ~maak~'s own tasks find the toolchain there
because ~~/.cargo/bin~ is on the session's PATH (see below).  The last line is
not decoration: the prompt runs =niri --session= as a login, with the
distribution's PATH and nothing else, so a binary left in =~/.cargo/bin= is a
session the prompt greys out.

Niri is built from git, not from a tarball, so an update is the same
~cargo install~ line again followed by the same ~install~.  The session entry
written in step 5 does not change.

*** X11, for the launcher
:PROPERTIES:
:CUSTOM_ID: debian-x11
:END:

Debian 13's =rofi= is 1.7.5 and speaks X11 only.  Niri has no X server of its
own, so a launcher key does nothing until one is there.  Since 25.08 Niri starts
=xwayland-satellite= itself, exports =DISPLAY= for everything it spawns and
restarts the satellite when it dies - so the whole of the setup is having the
binary on the PATH.  Debian 13 packages neither the satellite nor any version of
it, so it is built from its own source:

#+begin_src shell
sudo apt-get install --no-install-recommends build-essential pkg-config git clang \
    libxcb-cursor-dev libxcb1-dev
. "$HOME/.cargo/env"
cargo install --git https://github.com/Supreeeme/xwayland-satellite \
    xwayland-satellite
sudo install -Dm755 "$(command -v xwayland-satellite)" /usr/local/bin/xwayland-satellite
#+end_src

Niri needs satellite 0.7 or newer.  With the binary in place and the session
restarted, =rofi= opens under Niri; without it, the key is silent and no error is
printed.  Void ships =rofi= 2.0, which speaks Wayland itself, which is why this
section is Debian's alone.  The satellite does not need a unit file or a startup
line: Niri owns it.

*** The icon fonts
:PROPERTIES:
:CUSTOM_ID: debian-fonts
:END:

The bar draws its glyphs with =font_family="Font Awesome 6 Free Solid, Symbols
Nerd Font, FontAwesome"= - the 6 Free face first, then the two faces a Debian
machine is likely to have.  Debian 13 carries only the 4.7 release, whose family
is =FontAwesome=, and no symbols face at all, so a fresh machine draws a row of
hex boxes for the glyphs 4.7 does not have - which is most of the bar.

Both faces are free (SIL Open Font License) and neither is vendored here.
Install them for the account that runs the session:

#+begin_src shell
# Font Awesome 6 Free: download the desktop release, then
mkdir -p ~/.local/share/fonts
unzip -j ~/Downloads/fontawesome-free-*-desktop.zip \
  '*/webfonts/fa-solid-900.ttf' -d ~/.local/share/fonts

# Symbols Nerd Font: one file from the Nerd Fonts release
curl -fsSL -o /tmp/SymbolsNerdFont.tar.xz \
  https://github.com/ryanoasis/nerd-fonts/releases/latest/download/NerdFontsSymbolsOnly.tar.xz
tar -xJf /tmp/SymbolsNerdFont.tar.xz -C ~/.local/share/fonts

fc-cache -f
fc-list | grep -Ei 'Font Awesome 6|Symbols Nerd'
#+end_src

=fc-list= is the check: it should print a =Font Awesome 6 Free= line and a
=Symbols Nerd Font= line.  A bar started before the fonts were installed keeps
the boxes until it is restarted - =pkill waybar=, or log out and back in.
[[file:configuration.org][Configuration and customization]] has the family list
the bar asks for, which is what makes either face enough, and
=(whelk-icon-font ...)= for the shell's own.

*** The portal's back end
:PROPERTIES:
:CUSTOM_ID: debian-portal
:END:

=gnome-shell='s portal crashes (SIGSEGV) under Niri on Debian 13, and a client
waiting on it - the bar, for one - waits instead of drawing.  ~maak
home-reconfigure~ writes ~/.config/xdg-desktop-portal/niri-portals.conf~ naming
GTK's back end, which wants a portal host and not a desktop environment:

#+begin_src conf
[preferred]
default=gtk
org.freedesktop.impl.portal.Secret=gnome-keyring
org.freedesktop.impl.portal.ScreenCast=gnome
org.freedesktop.impl.portal.Screenshot=gnome
#+end_src

Change it if you want GNOME's back end for the file chooser; it is the portal's
file and the only place the choice is made.

*** Waybar's own service
:PROPERTIES:
:CUSTOM_ID: debian-waybar-service
:END:

Debian's =waybar= package enables =waybar.service= for the graphical session, so
a machine where the session starts the bar itself gets a second bar on top of the
first.  Turn the package's own off, once:

#+begin_src shell
systemctl --global disable waybar.service
#+end_src

*** The input method's environment
:PROPERTIES:
:CUSTOM_ID: debian-ibus
:END:

Debian's =im-config= exports X11 scrollback settings into every session, and on
Wayland they are what produce ~IBus should be called from the desktop session~ in
the log at every login.  Niri has no IBus session, and a machine that does not use
one can say so:

#+begin_src shell
im-config -n none
#+end_src

** When something does not work

*** =guix= is the installer's, not the pulled one

On a foreign distribution =/usr/local/bin/guix= is the installer's guix, which
knows only the default channels: asked to install a package from the collection,
it answers that the package does not exist.  The pulled one is
=~/.config/guix/current/bin/guix=, and ~maak~'s own tasks already use it.
By hand, name it: =~/.config/guix/current/bin/guix install maak~.

*** An apt install stops on a name

=apt-get install= resolves the whole list or none of it.  If ~maak install-apt~
stops on a name this Debian release does not have - a suite older than the list
was written for - install the rest by hand and say so in an issue; the list is
one file and one line is the difference.

*** The prompt says *Authentication failed* on every boot

The prompt is tuigreet, and its own file is why: it enables the remembered name
and *not* the user menu, because tuigreet 0.11.x sends two session requests when
both are on and greetd refuses the second.  If your =/etc/tuigreet/config.toml=
still carries a =[user_menu]= table, remove it.

** Updating

#+begin_src shell
maak update
#+end_src

~maak update~ runs every manager this machine has, at once, in one table: apt for
Debian's packages, Flatpak, Nix and Guix.  ~maak update-apt~ is Debian's alone -
=apt-get update= and then =apt-get upgrade=, which is the upgrade that will not
remove a package to make room.  ~maak check-updates~ asks all of them what would
change and installs nothing.
