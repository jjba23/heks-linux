The path is [[file:installation.org][Installation]] for a machine you install
yourself, and [[file:void-image.org][the image]] for the medium that installs
itself.  This page is the rest of it: the extras a session wants, and the places
where Void needs a second command or a package it does not carry.

* Emacs

If you want to learn Emacs, learn from scratch, with vanilla Emacs, and craft
your own configuration - it is the one editor where the configuration *is* the
editor, and somebody else's is a house you did not build.  When you would rather
see a finished one, [[https://codeberg.org/jjba23/heks-emacs][heks-emacs]] is
the one this project writes:

#+begin_src shell
  maak install-emacs-bridge   # ~/.emacs.d/heks-linux-bridge.el
#+end_src

The bridge is how Emacs learns the palette and the three fonts, so a palette
switch reaches it like every other surface.

Void packages three builds: ~emacs~ (terminal), ~emacs-gtk3~ and ~emacs-pgtk~.
This desktop is Wayland, so ~emacs-pgtk~ is the one to install:

#+begin_src shell
  sudo xbps-install -S emacs-pgtk
#+end_src

For the latest Emacs from master, build it yourself - the walkthrough is
[[https://jointhefreeworld.org/blog/articles/emacs/build-emacs-from-source/index.html][this
one]].  The toolchain is ~base-devel~ plus the libraries the graphical build
reads:

#+begin_src shell
  sudo xbps-install -S base-devel gtk+3-devel librsvg-devel sqlite-devel \
      libgccjit-devel gnutls-devel tree-sitter-devel libmagick-devel
#+end_src

* Flatpak and Flathub

Flatpak is a convenient containerised package format, and it is on the image and
in ~maak install-xbps~.  The Heks catalog lives in
~src/heks-linux/packages/flatpak.scm~ and every application is a declaration, not
a string: the id Flathub uses plus the remote it comes from.

#+begin_src scheme
  (define heks-linux-other-flatpak
    (make-parameter (list (flatpak-app "org.gnome.DejaDup")
                          (flatpak-app "org.keepassxc.KeePassXC")
                          ;; only needed from a beta remote:
                          (flatpak-app "org.example.Beta"
                                       #:remote "flathub-beta"))))
#+end_src

The remote defaults to Flathub, so the ordinary entry is just the id. The remote
belongs in its own field rather than inside the id because the installer uses it
to add the repository: every remote in the catalog is registered with
=flatpak remote-add --user --if-not-exists= before the first application is
installed - but only when no installation already has it, since a second
=flathub= makes some Flatpak commands ambiguous. The application ids are passed
to =flatpak install= as separate arguments, never as one shell string.

#+begin_src shell
  maak install-flatpak
#+end_src

The groups - dev, gaming, media, music, net, other and work - are parameters.
A machine adds its own applications with ~heks-linux-extra-flatpak~ in
~$XDG_CONFIG_HOME/heks-linux/flatpak-settings.scm~, which is evaluated in the
module's scope before the catalog is read:

#+begin_src scheme
  (heks-linux-extra-flatpak
   (list (flatpak-app "org.gnome.Fractal")))
#+end_src

Duplicates are removed by id, so an application that fits two groups is still
installed once. The extra list is read before the categories, so it can also
redeclare an existing id to change its remote. Update the set with:

#+begin_src shell
  maak update-flatpak
#+end_src

** Cleaning every Flatpak's font cache

A font copied into ~~/.local/share/fonts~ is visible to the host and invisible
inside a sandbox until that sandbox's cache is rebuilt.  This runs =fc-cache= in
each of them:

#+begin_src shell
  flatpak list --columns=application |
      xargs -I %s -- flatpak run --command=fc-cache %s -frv
#+end_src

* Nix

Nix is useful for development and for the packages Void does not carry.  The
nixpkgs channel is not what this tree installs from - the flake at the root of
the checkout is, and its ~flake.lock~ pins the revision - but a one-off is still
one command:

#+begin_src shell
  nix search nixpkgs k6
  nix profile install nixpkgs#k6
#+end_src

Heks declares what the desktop needs from Nix so it is not installed by hand:
~maak install-nix-packages~ reads ~src/heks-linux/packages/nix.scm~ and installs
them into the Nix profile.

#+begin_src shell
  maak install-nix-packages
#+end_src

The installable is ~.#<attribute>~, not ~nixpkgs#<attribute>~: the flake at the
root of the checkout is where the packages come from, and its ~flake.lock~ is
what pins them. The registry entry ~nixpkgs#~ answers with whatever nixpkgs it
currently points at, which is a different set of builds on the next machine and
on the next day; the lock is the same one everywhere. ~maak install-heks-toon~
installs its ~.#heks-toon~ the same way.

Moving the pins is one command each: ~nix flake update~ re-locks every input,
~nix flake update nixpkgs~ just the one, and ~maak update-nix~ then upgrades the
profile to what the new lock says. A package installed from ~nixpkgs#~ before
this flake existed is installed again from ~.#~ the next time the task runs, so a
machine that had been following the registry stops following it.

The list holds what Void has no package for: the editor's language servers -
~yaml-language-server~ for YAML, ~nil~ for Nix, ~marksman~ for Markdown and
~vscode-langservers-extracted~ for JSON, CSS and HTML - the readers for disk
images (~undmg~ unpacks a ~.dmg~ into the HFS+ volume inside it, and ~hfsprogs~
supplies ~fsck.hfsplus~ and ~mkfs.hfsplus~ for that volume), ~whelk~ because no
Void repository carries the shell, the Rust components a ~rustup~ toolchain only
grows on request, Kotlin and Gradle with the two JVM language servers, the
database shells - ~pgcli~, ~mycli~, ~usql~, ~dbeaver-bin~, ~duckdb~ and
~sqlite-utils~ - and the Guile modules Void has no package for. A package the
profile already holds is skipped, so the task is safe to re-run.

A machine that wants more adds it in
~$XDG_CONFIG_HOME/heks-linux/nix-settings.scm~, which is evaluated in the
module's scope before the list is read:

#+begin_src scheme
  (heks-linux-language-server-nix
   (cons (nix-package "zls") (heks-linux-language-server-nix)))
#+end_src

* Podman and containers

Podman is in ~maak install-xbps~.  Heks renders its registries and policy files:

#+begin_src shell
  maak install-containers-config
#+end_src

Distrobox runs a Debian container on top of that Podman, for the programs that
ship only as a =.deb=.  It shares the host's home, the Wayland socket, the
PipeWire socket and the GPU, so a program installed inside it uses this session's
audio and screen.  Void has no package for Distrobox itself, so install it from
[[https://github.com/89luca89/distrobox][its own releases]] first:

#+begin_src shell
  maak install-distrobox
  heks-deb create
  heks-deb install ~/Downloads/thing_amd64.deb
#+end_src

[[file:distrobox.org][docs/distrobox.org]] has the whole story - what the manifest
installs, how to check that sound and the GPU arrived, and what to change on a
machine that wants another image or the NVIDIA driver.

* Browsers: Zen, Firefox and Chrome

Zen Browser is the daily driver. It is declared in
~src/heks-linux/packages/flatpak.scm~, so the normal Flatpak task installs it:

#+begin_src shell
  maak install-flatpak
  flatpak run app.zen_browser.zen   # once, so that Zen creates a profile
  maak install-zen
#+end_src

Quit Zen before ~maak install-zen~: the profile is read at startup, and the
side-loaded uBlock Origin build is picked up on the next launch. See
[[file:zen-browser.org][the Zen deep dive]] for what the generated file contains
and how to change it.

Firefox is Void's own package, and Chrome comes from Google:

#+begin_src shell
  sudo xbps-install -S firefox
#+end_src

* 1Password

1Password is not a Void package and it is not in the Flatpak catalog either,
because it is installed from the vendor.  The Flatpak is the one that keeps
itself up to date:

#+begin_src shell
  flatpak install https://downloads.1password.com/linux/flatpak/1Password.flatpakref
#+end_src

That build is not a command called =1password=, so a machine that installs it
this way points the desktop's one password setting at it - which the session's
login line and the bar's key glyph both read:

#+begin_src scheme
  ;;; ~/.config/heks-linux/local-settings.scm
  (heks-linux-password-command "flatpak run com.onepassword.OnePassword")
#+end_src

* WireGuard

~wireguard-tools~ is the whole requirement:

#+begin_src shell
  sudo xbps-install -S wireguard-tools
#+end_src

A tunnel is a file in =/etc/wireguard=, and NetworkManager is what brings it up
at boot on a machine that has no init service for it - import the file once and
it is a connection like any other:

#+begin_src shell
  sudo mv ~/Downloads/laptop-nl.conf /etc/wireguard/wg0.conf
  sudo nmcli connection import type wireguard file /etc/wireguard/wg0.conf
  nmcli connection up wg0        # and it comes up on its own from then on
#+end_src

Without NetworkManager, ~wg-quick up wg0~ is the same tunnel for this session
only, and it goes away with the reboot.  ProtonVPN has no Void package: their
Flatpak is the maintained client there, and a WireGuard profile exported from
their dashboard needs nothing but the two commands above.
